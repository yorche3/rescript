# Naive Sort — ReScript

Implementación de la especificación [05_Naive_Sort](https://yorche3.github.io/programming_languages/core/algorithms/05_Naive_Sort/) en **ReScript**, con **Jest** y los bindings **@glennsl/rescript-jest** como framework de pruebas unitarias.

Tres algoritmos de ordenación con coste $O(n^2)$: **selection sort**, **bubble sort** e **insertion sort**, los tres *in-place* sobre el `array<int>` recibido, sin invocar `Array.sort`, `Belt.Sort` ni ninguna biblioteca de ordenamiento.

### `src/naive_sort.res` — Implementación

**ES:** Las tres funciones reciben un `array<int>`, lo ordenan y devuelven ese mismo array. Extracto de `bubble_sort`, que conserva la bandera de intercambio y la salida temprana del pseudocódigo:

**EN:** All three functions take an `array<int>`, sort it and return that same array. Excerpt from `bubble_sort`, which keeps the swap flag and the pseudocode's early exit:

```rescript
let selection_sort = (array: array<int>) => {
  let n = Array.length(array);
  for i in 0 to n - 2 {
    let min_index = ref(i);
    for j in i + 1 to n - 1 {
      if array[j] < array[min_index.contents] {
        min_index := j;
      }
    };
    if min_index.contents != i {
      let temp = array[i];
      array[i] = array[min_index.contents];
      array[min_index.contents] = temp;
    }
  };
  array;
};
```

| Algoritmo | Estrategia implementada |
| --------- | ----------------------- |
| `selection_sort` | `for i in 0 to n - 2` con `min_index` en un `ref` y swap guardado por `if min_index.contents != i` |
| `bubble_sort` | `while` por pasada con `swapped` en un `ref`: la bandera es la condición del bucle, así que sale sola al no haber intercambios |
| `insertion_sort` | `key` + `while j.contents >= 0 && array[j.contents] > key` que desplaza el sub-tramo ordenado |

### Suites de pruebas — rescript-jest

**ES:** Una única suite con un `describe` por algoritmo. Los 7 casos viven en una lista de tuplas compartida y un único helper los recorre para cualquier función; como `expect` de Jest no acepta un mensaje, el mensaje del contrato se compone con el nombre del `describe` y el del `test`, y cada caso ordena una **copia** del fixture:

**EN:** A single suite with one `describe` per algorithm. The 7 cases live in a shared tuple list and a single helper walks them for any function; since Jest's `expect` takes no message, the contract message is composed from the `describe` and `test` names, and each case sorts a **copy** of the fixture:

```rescript
// Helper compartido: recibe la función a probar y el nombre del algoritmo, y
// ejecuta todos los casos. El nombre del `describe` y el del `test` componen el
// mensaje del contrato ("{algoritmo} should sort {descripción}"), porque Jest no
// admite un mensaje como argumento de `expect`.
let assert_sorts_all_cases = (sort, algorithm) =>
  describe(algorithm, () => {
    cases->Belt.Array.forEach(((description, input, expected)) =>
      test("should sort " ++ description, () =>
        expect(sort(Belt.Array.copy(input)))->toEqual(expected)
      )
    )
  })

assert_sorts_all_cases(Naive_sort.selection_sort, "selection_sort")
assert_sorts_all_cases(Naive_sort.bubble_sort, "bubble_sort")
assert_sorts_all_cases(Naive_sort.insertion_sort, "insertion_sort")
```

> **ES:** Jest ya incluye su propio runner, así que no se crea el `run_tests` del pseudocódigo (la especificación lo pide solo si el framework no lo incluye); el punto de entrada es `npm test`.
> **EN:** Jest already includes its own runner, so the pseudocode's `run_tests` is not created (the specification asks for it only if the framework doesn't include one); the entry point is `npm test`.

## 🧠 Algoritmos y operaciones / Algorithms & Operations

| Algoritmo | Función | Estrategia | Entrada ordenada | Entrada invertida |
|-----------|---------|-----------|:----------------:|:-----------------:|
| Selection sort | `selection_sort` | Busca el mínimo del tramo no ordenado con `min_index` y lo intercambia al inicio | $O(n^2)$ | $O(n^2)$ |

## 📝 Notas de implementación / Implementation Notes

### 🧬 Ordenamiento *in-place* sobre el array recibido / In-place sorting over the received array

**ES:** El pseudocódigo ordena el propio array con `swap(arr, i, j)`, y en ReScript los arrays son **mutables**: las tres funciones ordenan el array que reciben (`array[i] = …`) y lo devuelven, así que el contrato se cumple en su variante *in-place*. Por eso la suite ordena una **copia** del fixture en cada caso (`Belt.Array.copy(input)`) y no puede contaminar los siguientes.

**EN:** The pseudocode sorts the array itself with `swap(arr, i, j)`, and in ReScript arrays are **mutable**: all three functions sort the array they receive (`array[i] = …`) and return it, so the contract is met in its *in-place* variant. That is why the suite sorts a **copy** of the fixture in each case (`Belt.Array.copy(input)`) and cannot contaminate the next ones.

### 🚫 Caso nulo omitido: `array<int>` no admite `null` / Null case omitted: `array<int>` does not accept `null`

**ES:** La especificación pide devolver el indicador de fallo si la entrada es nula o inválida. El tipo `array<int>` de ReScript **no admite `null`** ni una entrada inválida, así que el caso no es representable en la firma y se conservan los 7 casos obligatorios, con el array vacío como caso 7: los tres bucles no iteran con `n <= 1` y el array vacío se devuelve tal cual, sin lanzar excepciones.

**EN:** The specification requires returning the failure indicator when the input is null or invalid. ReScript's `array<int>` type **does not admit `null`** or an invalid input, so the case is not representable in the signature and the 7 mandatory cases are kept, with the empty array as case 7: the three loops do not iterate when `n <= 1` and the empty array is returned as is, without throwing exceptions.

### 🔁 `bubble_sort` y la bandera de intercambio / `bubble_sort` and the swap flag

**ES:** El criterio de aceptación exige la optimización de salida temprana. `bubble_sort` lleva `swapped` en un `ref` y **la usa como condición del `while`**: la pasada externa solo se repite mientras la bandera siga siendo `true` (`while swapped.contents && i.contents <= n - 2`), que es exactamente el `if not swapped then break` del pseudocódigo, de modo que un array ya ordenado se resuelve en **una sola pasada** y el mejor caso es $O(n)$. La bandera **no es observable en la salida** (las tres funciones devuelven un array ordenado), así que la suite no puede detectar su ausencia: su presencia se verifica comparando el código con el pseudocódigo.

**EN:** The acceptance criteria require the early-exit optimisation. `bubble_sort` keeps `swapped` in a `ref` and **uses it as the `while` condition**: the outer pass only repeats while the flag is still `true` (`while swapped.contents && i.contents <= n - 2`), which is exactly the pseudocode's `if not swapped then break`, so an already sorted array is solved in **a single pass** and the best case is $O(n)$. The flag is **not observable in the output** (all three functions return a sorted array), so the suite cannot detect its absence: its presence is verified by comparing the code against the pseudocode.

### ➿ Sintaxis de ReScript 11: `to` y `ref` / ReScript 11 syntax: `to` and `ref`

**ES:** El proyecto fija `rescript ^11.1.4` (la misma versión que `numbers/`), así que el código usa la sintaxis de esa versión: los bucles se escriben con `for i in 0 to n - 2 { … }` (no con rangos `..`), los acumuladores mutables son **referencias** (`let min_index = ref(i)`, asignación `min_index := j`, lectura `min_index.contents`) y la salida temprana de bubble va en la condición del `while`, porque esta versión **no tiene `break`**. Los bucles `for i in 1 to n` con `n = 0` no iteran (inicio mayor que fin), como en el pseudocódigo.

**EN:** The project pins `rescript ^11.1.4` (the same version as `numbers/`), so the code uses that version's syntax: loops are written with `for i in 0 to n - 2 { … }` (not with `..` ranges), mutable accumulators are **references** (`let min_index = ref(i)`, assignment `min_index := j`, read `min_index.contents`) and bubble's early exit lives in the `while` condition, because this version **has no `break`**. Loops `for i in 1 to n` with `n = 0` do not iterate (start greater than stop), as in the pseudocode.

### 🔀 Estabilidad de `insertion_sort` / `insertion_sort` stability

**ES:** El desplazamiento usa la comparación estricta `array[j.contents] > key` con la guarda `j.contents >= 0`, así que los elementos iguales conservan su orden relativo y `insertion_sort` es estable. El caso 1 (`[5, 2, 9, 1, 5, 6]`, con dos cincos) se beneficia de ello, aunque los tests comparan valores y no identidad.

**EN:** The shifting uses the strict comparison `array[j.contents] > key` with the `j.contents >= 0` guard, so equal elements keep their relative order and `insertion_sort` is stable. Case 1 (`[5, 2, 9, 1, 5, 6]`, with two fives) benefits from it, although the tests compare values rather than identity.

### 🏷️ Naming y mensajes de aserción / Naming and assertion messages

**ES:** Las funciones usan `snake_case` (`selection_sort`), que coincide con el nombre de la especificación, y el módulo que genera el compilador a partir del fichero es `Naive_sort` (la primera letra se capitaliza; de ahí las llamadas `Naive_sort.selection_sort`). Jest no admite un mensaje como argumento de `expect`, así que el mensaje del contrato se compone con el nombre del `describe` (el algoritmo) y el del `test` (`should sort <descripción>`): el reporte de un fallo muestra `● selection_sort › should sort an unsorted array`.

**EN:** Functions use `snake_case` (`selection_sort`), matching the specification's name, and the module the compiler derives from the file is `Naive_sort` (the first letter is capitalised; hence the `Naive_sort.selection_sort` calls). Jest takes no message argument in `expect`, so the contract message is composed from the `describe` name (the algorithm) and the `test` name (`should sort <description>`): a failure is reported as `● selection_sort › should sort an unsorted array`.
